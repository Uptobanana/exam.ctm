# 中医出师考核学习工具 · 用户系统设计文档

**日期**：2026-07-29
**阶段**：阶段一（认证 + 数据基础）
**目标用户规模**：小范围（几十人）起步，架构可平滑演进
**部署平台**：腾讯云 CloudBase 云开发

---

## 一、概述

### 1.1 背景

当前工具为纯静态前端（`index.html` + `app.js` + 9个科目JS），所有学习数据（进度、收藏、错题、练习历史、学习路径）存在浏览器 `localStorage`，无后端、无数据库。已部署在 CloudBase 静态托管。

现需加入用户系统：不同人用账号密码登录后独立使用，学习数据与用户绑定；管理员（你）能管理用户、查看日志、发站内通知。

### 1.2 设计目标

- 用户可注册、登录，学习数据按用户隔离并云端持久化
- 老用户本地 `localStorage` 数据可迁移上云，不丢失进度
- 前端业务逻辑（app.js）改动最小化
- 零服务器运维，几十人规模几乎零成本
- 为阶段二（管理后台）、阶段三（站内通知）预留扩展点

### 1.3 分阶段范围

| 阶段 | 内容 | 状态 |
|------|------|------|
| **阶段一** | 认证 + 数据基础：注册登录、用户数据模型、数据同步与迁移 | 本文档设计 |
| **阶段二** | 管理后台：用户管理、使用日志查看、密码重置 | 预留接口，后续设计 |
| **阶段三** | 站内通知：管理员发通知、用户接收 | 预留接口，后续设计 |

本文档聚焦阶段一，同时对阶段二/三的接口预留做说明。

## 二、技术路线与部署路线

### 2.1 技术路线

**CloudBase 云开发：云函数 + 云数据库（NoSQL）+ 自定义账号密码登录**

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | 现有静态站点 + CloudBase JS SDK | 静态托管不变，加 SDK 与少量调用代码 |
| 后端逻辑 | 云函数（Node.js） | 承载注册登录、管理员操作 |
| 数据存储 | 云数据库（NoSQL 文档型） | 学习数据每人一个 JSON 文档 |
| 认证 | 自定义登录 | 云函数校验账号密码 + 平台发凭证 |

**选型理由**：全部能力已在现有 CloudBase 控制台，零新增平台、零服务器运维；NoSQL 天然契合现有 JSON 学习数据，无需设计表结构；几十人规模按量计费基本免费；将来扩容可平滑扛住或迁移。

### 2.2 部署路线

| 部分 | 开发方式 | 部署方式 |
|------|---------|---------|
| 云函数（后端） | 本地写 Node.js | `tcb` CLI 一条命令部署到当前环境 |
| 云数据库 | 控制台建集合 + 设权限规则 | 控制台配置，无需部署代码 |
| 前端静态站点 | 本地改 HTML/JS | 继续现有压缩包上传或改用 CLI |

**开发节奏**：本地写云函数 → `tcb fn deploy` 上传 → 前端调用。改前端则重传静态站点。整个闭环在同一 CloudBase 环境内完成。

**前置准备**：本地安装 Node.js（云函数运行时）+ `@cloudbase/cli`（`npm install -g @cloudbase/cli`）。

```
┌────────────────────────────┐         CloudBase SDK          ┌──────────────────────────────┐
│  前端（静态托管，基本不动）  │  ◄──────────────────────────►  │  CloudBase 云开发（同一环境）  │
│  index.html / app.js        │                                │                              │
│  subjects/*.js              │   ① 调用云函数（注册/登录）     │  云函数                      │
│  + auth-client.js（新增）   │   ② 直连云数据库（读写自己的数据）│   ├─ register                │
│  + sync-client.js（新增）   │                                │   ├─ login                   │
│  + @cloudbase/js-sdk        │                                │   └─ initAdmin（引导）        │
└────────────────────────────┘                                │                              │
                                                              │  云数据库（NoSQL）            │
                                                              │   ├─ users（凭证，前端不可见） │
                                                              │   ├─ user_data（每人学习数据）│
                                                              │   └─ audit_logs（审计日志）   │
                                                              └──────────────────────────────┘
```

**职责划分**：

- **前端**：保持现有静态站点，新增 `auth-client.js`（登录注册界面与状态管理）、`sync-client.js`（数据同步层）。`app.js` 业务逻辑几乎不动，继续用 `localStorage` 当工作副本，sync-client 在背后镜像云端。
- **云函数**：承载需要管理员权限的逻辑（注册、登录、引导建管理员）。数据同步走前端直连云数据库（受安全规则约束），不走云函数，减少代码与冷启动。
- **云数据库**：三个集合，凭证与学习数据分离，权限规则各管各。

## 四、云数据库集合设计

### 4.1 集合 `users`（用户凭证，敏感）

每个注册用户一个文档：

```json
{
  "_id": "自动生成的唯一ID",
  "username": "张三",
  "password_hash": "bcrypt 哈希字符串",
  "role": "user",
  "status": "active",
  "created_at": 1722200000000,
  "last_login_at": 1722200000000
}
```

字段说明：
- `username`：唯一，登录用，建索引
- `password_hash`：bcrypt 哈希，绝不存明文
- `role`：`user` 普通用户 / `admin` 管理员
- `status`：`active` 正常 / `disabled` 禁用（禁用后无法登录）
- `last_login_at`：最近登录时间，供阶段二管理后台展示

**权限规则**：`{ "read": false, "write": false }` —— 禁止前端直接访问，仅云函数（管理员权限）可读写。这是系统安全底线，密码哈希绝不暴露给前端。

### 4.2 集合 `user_data`（学习数据，每人一份）

每个用户一个文档：

```json
{
  "_id": "等于该用户的 uid",
  "learning_data": { },
  "updated_at": 1722200000000
}
```

字段说明：
- `_id`：等于该用户的 CloudBase `auth.uid`（即 `users._id`），天然关联
- `learning_data`：一整块 JSON，包含现有 localStorage 的全部键：`syllabus_v4`、`syllabus_v4_favs`、`quizHistory`、`syllabus_v4_learned`、`perf`、`studyProgress`
- `updated_at`：最近一次写入时间，用于多设备冲突判定

**权限规则**：`{ "read": "doc._id == auth.uid", "write": "doc._id == auth.uid" }` —— 前端只能读写自己的那一个文档，由平台强制隔离。

### 4.3 集合 `audit_logs`（审计日志，为阶段二预备）

```json
{
  "_id": "自动",
  "user_id": "操作者uid",
  "username": "张三",
  "action": "login",
  "timestamp": 1722200000000,
  "detail": { }
}
```

`action` 取值：`register`、`login`、`logout`、`saveData`（可选）、`admin_*`（阶段二）。

**权限规则**：`{ "read": false, "write": false }` —— 禁止前端访问，仅云函数写入与（阶段二）查询。

### 4.4 关键设计点

1. **凭证与学习数据分离**：`users`（前端不可见）和 `user_data`（本人可读写）分开，权限规则各管各，安全清晰。
2. **uid 作关联主键**：注册时云函数生成 uid 作为 `users._id`；自定义登录后此 uid 即 CloudBase `auth.uid`；`user_data._id` 也用它。三者天然对齐，无需额外关联字段。
3. **学习数据单文档 JSON 大块**：不拆成进度表/收藏表/错题表。前端本就整体读写，一人一个文档，简单直接。

## 五、云函数设计

### 5.1 阶段一云函数

**`register`（注册）**

- 输入：`{ username, password }`
- 逻辑：
  1. 校验用户名格式（3-20位字母数字下划线）、密码长度（≥6）
  2. 查 `users` 集合，用户名已存在则返回错误
  3. bcrypt 哈希密码
  4. 插入 `users` 文档（`role=user`，`status=active`）
  5. 写 `audit_logs`（action=register）
  6. 用管理员 SDK 生成自定义登录 ticket，返回 `{ ticket, uid }`
- 输出：`{ ok: true, ticket, uid }` 或 `{ ok: false, error }`

**`login`（登录）**

- 输入：`{ username, password }`
- 逻辑：
  1. 查 `users`，用户名不存在或密码不匹配 → 统一返回"用户名或密码错误"（防探测）
  2. `status=disabled` → 返回"账号已禁用"
  3. 更新 `last_login_at`
  4. 写 `audit_logs`（action=login）
  5. 生成自定义登录 ticket 返回
- 输出：`{ ok: true, ticket, uid, role }` 或 `{ ok: false, error }`

**`initAdmin`（引导建管理员，一次性）**

- 输入：`{ username, password }`
- 逻辑：
  1. 校验当前 `users` 集合是否已有 admin（防重复创建）
  2. 创建 `role=admin` 的用户文档
  3. 写 `audit_logs`（action=register, detail.role=admin）
- 调用方式：通过 `tcb` CLI 或控制台云函数测试入口手动调用一次，用你选的账号密码建号。此函数也可设为仅管理员可调，但首次无管理员时需通过 CLI 触发。

### 5.2 数据同步：不走云函数

学习数据的读写由前端通过 CloudBase JS SDK 直连 `user_data` 集合完成，受安全规则约束（仅本人文档）。理由：学习数据是"整体读整体写"的自有数据，无需服务端校验；直连减少云函数代码与冷启动延迟。

> 备选：若后续需要在保存时做服务端校验或写审计日志，可加 `syncData` 云函数。阶段一先用直连。

### 5.3 阶段二云函数（预留，阶段二再实现）

- `adminListUsers`：分页列出用户
- `adminToggleUserStatus`：启用/禁用账号
- `adminResetPassword`：管理员重置密码
- `adminGetLogs`：查询审计日志

均需校验调用者 `role=admin`。

## 六、认证流程（自定义账号密码登录）

### 6.1 自定义登录原理

CloudBase 原生认证支持匿名、邮箱、手机、微信，但无现成"账号密码"。采用"自定义登录"：

1. 前端提交用户名密码到 `login` 云函数
2. 云函数校验通过后，用管理员 SDK 生成自定义登录 ticket
3. 前端调用 `app.auth().signInWithTicket(ticket)` 完成登录
4. 登录后前端获得 CloudBase `auth.uid`（等于 `users._id`），后续直连数据库时平台自动识别身份

> 说明：自定义登录 ticket 的生成 API（`@cloudbase/node-sdk` 的 `auth().createTicket()`）在实现时按 CloudBase 最新文档确认。设计层面保证"云函数校验 + 平台发凭证"的流程不变。

### 6.2 登录状态持久化

- CloudBase SDK 支持指定 persistence：`'local'`（浏览器关闭后仍保留）、`'session'`（关闭即登出）、`'none'`（不保留）
- 登录页"记住我"勾选 → `local`；不勾 → `session`
- 应用启动时检查 `app.auth().currentUser`，已登录则直接进应用

### 6.3 注册/登录/登出流程

```
注册：
  前端校验 → register 云函数 → 成功返回 ticket → signInWithTicket → 进应用

登录：
  前端校验 → login 云函数 → 成功返回 ticket → signInWithTicket → 加载云端数据 → 进应用

登出：
  app.auth().signOut() → 清除登录态 → 回到登录页
```

## 七、前端设计

### 7.1 新增文件 `auth-client.js`（认证界面与状态管理）

**登录/注册页**：一个覆盖层，应用启动时先检查登录状态。未登录显示此页，已登录进应用。两种模式可切换：

- 注册：用户名 + 密码 + 确认密码
- 登录：用户名 + 密码 + "记住我"

**前端校验**：用户名 3-20 位字母数字下划线、密码 ≥6 位、两次密码一致。不通过则输入框下方红字提示，不调用云函数。

**登录反馈（重点）**：

- 提交后立即显示"加载中"（云函数有冷启动，避免重复点击）
- 成功 → 进入应用
- 用户名已存在（注册）→ 用户名输入框红字提示
- 用户名或密码错误（登录）→ 统一报错，不区分"用户名不存在"与"密码错"（防探测）
- 账号已禁用 → 提示联系管理员
- 网络异常 → "网络异常请重试"

**账号入口**：顶部导航栏加账号入口，显示用户名 + 退出登录按钮。

### 7.2 新增文件 `sync-client.js`（数据同步层）

核心原则：**app.js 继续用 `localStorage` 当工作副本，sync-client 在背后镜像云端**。

- **登录后加载**：从 `user_data` 集合读取本人文档，把 `learning_data` 写入 `localStorage`，app.js 像往常一样从 `localStorage` 读。
- **改动后保存**：app.js 每次写 `localStorage` 时，sync-client 防抖（停顿 2 秒）后把整块 `learning_data` 写回云端。避免每点一下就上传。
- **离线容忍**：网络断了先存本地，连上后再同步。

### 7.3 `app.js` 改动（最小化）

仅三处挂钩子：

1. **应用启动**：检查登录态，未登录显示登录覆盖层
2. **登录成功后**：触发 `sync-client.loadFromCloud()` 加载云端数据并刷新界面
3. **`save()` 函数内**：加一行 `syncClient.scheduleSave()`（防抖同步）

现有几百行业务逻辑全部保留。

### 7.4 `index.html` 改动

- 引入 CloudBase JS SDK（CDN 或本地文件）
- 新增登录覆盖层容器
- 顶部导航栏加账号入口
- 引入 `auth-client.js`、`sync-client.js`

## 八、数据同步与迁移

### 8.1 登录后数据加载与迁移逻辑

登录成功后，sync-client 执行：

```
cloud_data = 读 user_data 文档（本人）
local_data = 当前 localStorage

若 cloud_data 为空 且 local_data 有数据：
    → 老用户首次上云：弹提示"检测到本机有学习记录，是否上传到您的账号？"
    → 确认后把 local_data 作为初始云端数据上传

若 cloud_data 有数据 且 local_data 为空：
    → 新设备首次登录：下载 cloud_data 写入 localStorage

若两者都有数据：
    → 比较 updated_at 时间戳，取较新的一份
    → 若本地较新：提示"本机记录更新，是否覆盖云端？"确认后上传
    → 若云端较新：提示"云端记录更新，已同步到本机"，下载覆盖本地
    → （实现可简化为：直接按时间戳取新，并提示用户发生了同步方向）
```

### 8.2 保存逻辑

app.js 每次 `save()` → sync-client 重置 2 秒防抖计时器 → 计时器到期后整块写回 `user_data`，并更新 `updated_at`。

### 8.3 多设备一致性

同一账号在多设备使用时，每次登录都拉取最新云端数据；保存时以 `updated_at` 判定新旧。阶段一采用"最后写入胜出 + 时间戳"，不做细粒度合并。几十人规模下足够。

## 九、安全与防滥用

| 风险 | 措施 |
|------|------|
| 密码泄露 | bcrypt 哈希存储，绝不存明文；`users` 集合前端不可见 |
| 暴力破解登录 | `login` 云函数加限流：同一来源短时间内失败超阈值则拒绝（基于 IP / 用户名计数） |
| 注册机灌水 | `register` 云函数加限流：同一 IP 单位时间注册次数上限；用户名格式约束 |
| 账号探测 | 登录失败统一返回"用户名或密码错误"，不区分两者 |
| 越权访问 | `user_data` 安全规则强制 `doc._id == auth.uid`；`users`/`audit_logs` 前端不可见 |
| 管理员接口越权 | 阶段二所有 `admin_*` 云函数首步校验 `role=admin` |
| 密码找回 | 账号密码无邮箱手机，无法自助找回；阶段二由管理员重置密码 |
| 传输安全 | CloudBase 默认 HTTPS |

## 十三、风险与注意事项

1. **自定义登录 API 变更**：CloudBase 自定义登录 ticket 生成方式以官方最新文档为准，实现时确认 `@cloudbase/node-sdk` 的 `createTicket` 用法。
2. **冷启动延迟**：云函数首次调用有冷启动，前端必须做加载态，避免用户重复点击。
3. **限流实现**：云函数限流可基于 `audit_logs` 或独立计数集合，注意云函数无状态，需用数据库计数。实现时确认方案。
4. **数据迁移冲突**：老用户多设备都有本地数据时，阶段一用时间戳最后写入胜出，不做细粒度合并。若实际出现数据丢失投诉，阶段二再细化合并策略。
5. **bcrypt 依赖**：云函数需引入 `bcryptjs`（纯 JS 实现，云函数环境兼容），打包时随函数上传。
6. **前端缓存**：登录态与学习数据在 `localStorage`，退出登录时需明确清理策略（清学习数据，避免下一用户看到上一用户进度）。
7. **环境隔离**：建议先用测试环境验证，再推生产环境，避免影响现有静态站点用户。
